# WO-003 application foundation acceptance

Issue [#3](https://github.com/nhattruong0204/wallet-observer/issues/3). Verified on
2026-10-03 in the pinned Linux devcontainer as the non-root developer user.

## Delivered behavior

- FastAPI process provides liveness, authenticated database readiness, an
  allowlisted status response and built frontend serving.
- A separate asynchronous worker process runs dependency checks with its own
  local health endpoints and graceful shutdown. Collection and delivery remain disabled.
- React/Vite renders loading, honest empty fixture mode, database-offline and
  API-offline states. Retry and polling restore the connected state.
- Typed settings distinguish required database configuration, optional secrets,
  modes and reserved feature flags. Unsupported enabled integrations fail closed.
- API/worker JSON logs identify service and event without raw URLs, configuration
  values or exception text. No server environment is automatically exposed to Vite.
- Root Python/npm workspaces have committed locks; backend, frontend and debugger
  entrypoints plus the documented Make commands are executable.

## Verification evidence

`make lint test fixtures build test-ui` passed Ruff, ESLint, TypeScript, Prettier,
47 Python tests, 4 frontend tests, 3 browser tests and seven existing source
fixture checks. Python uses 3.12.15; Node uses 24.21.0. The backend wheel/sdist
build and Vite production build both succeeded.

The browser checks use pinned Playwright 1.63.0 / Chromium and real local
API/PostgreSQL services. All three passed:

1. Desktop loads the empty fixture state, detects browser offline, then reconnects
   through the visible retry control.
2. Mobile at 390px has no horizontal overflow and exposes fixture mode.
3. Disposable environment, watchlist and private-data files are refused by Vite
   with 403 responses and never returned to the browser.

Desktop, mobile and offline screenshots are local ignored artifacts under
`test-results/`; desktop and mobile were visually inspected. Playwright's graceful
SIGTERM teardown leaves ports 8000, 8001 and 5173 closed.

Real service lifecycle checks used the isolated `wallet-observer-wo003` Compose
project, preserving any other development database:

| Experiment                                                                 | Observed result                                                          |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Run `make dev` with provider/Telegram environment values explicitly empty  | API, worker and frontend started; API/worker readiness both 200          |
| Stop this project's PostgreSQL container                                   | API/worker readiness both 503; liveness both 200                         |
| Restart PostgreSQL                                                         | Readiness both returned to 200 without restarting API/worker             |
| Request API root after frontend build                                      | Built Wallet Observer HTML returned at port 8000                         |
| Send Ctrl-C to the development process group                               | All three service ports closed; API/worker start and stop events present |
| Terminate worker child unexpectedly                                        | Supervisor exited 1 and stopped API/frontend siblings                    |
| Invalid database URL or mode through the real CLI                          | Exit 2, field-specific errors, sentinel values absent                    |
| Scan runtime log and built frontend against configured integration secrets | No secret matches; runtime log contains no credential-bearing URL        |

The bounded database check issues only `SELECT 1`; it does not create a schema.
The loss/recovery check used `docker compose -p wallet-observer-wo003 -f
compose.dev.yml stop db` and `up -d --wait db`, then probed the two health ports
from inside the devcontainer. It did not interrupt a production database.

Offline tests cover configuration precedence, missing/invalid fields, integration
gates, log redaction (including malformed library extras), HTTP readiness
transitions, sanitized 500 errors, built-asset routing, worker recovery, stale or
failed loops, graceful stop, and frontend error/retry behavior. Existing tooling
and real-source fixture checks remain intact. No paid provider probe or Telegram
message was sent for this issue.

## Reproduction

Follow [development setup](../development.md) and the
[configuration contract](../configuration.md). Run from the repository root in
the devcontainer:

```bash
make bootstrap
make doctor
make config-check
make lint test fixtures build
npx playwright install --with-deps chromium
make test-ui
make dev
```

Stop separately running application services before `make test-ui`, which owns
its own startup/shutdown. Browser installation downloads software; runtime fixture
mode contacts only the local database and services. Default `make test` needs
neither provider credentials nor a running database/browser.

## Definition of done

- [x] API, worker and frontend start with documented commands.
- [x] Invalid settings fail with useful, redacted errors.
- [x] Fixture mode runs without provider or Telegram credentials.
- [x] API/worker logs contain service/event identifiers and exclude secret values
      and credential-bearing URLs.
- [x] Exact dependency declarations, workspace locks and a concise directory map
      are committed with the change.

Limits: this is the application foundation, not the first-live release. Schema
migrations, durable jobs, real collection, normalization, alerts and the complete
feed are subsequent issues. Fixture mode intentionally shows an empty feed rather
than interpreting provider fixtures as completed application trades. Worker
readiness is cached until its next bounded dependency check. Deployment,
authentication and richer operational diagnostics remain separate work. The
backend wheel does not contain frontend assets; repository-root execution serves
`frontend/dist` after a build. Windows/WSL was not separately exercised. CI setup
belongs to issue #15; the checks here ran locally in the pinned container.
