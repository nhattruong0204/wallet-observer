# [WO-029] Qualify RayBot access, payload semantics, and delivery guarantees

<!-- wallet-observer-task:WO-029 -->

**Milestone:** Optional RayBot

**Priority:** Qualification first; optional to the existing first-live release.

**Website first:** Desktop-browser website and supporting services only. Native mobile, installable PWA, device push and mobile acceptance remain deferred. Monitoring is read-only; no execution, signing keys, new chains or subscription upgrades are authorized.

**Assessment:** [RayBot feasibility review](https://github.com/nhattruong0204/wallet-observer/blob/main/docs/raybot-integration-assessment.md) (documentation review; no account probe performed).

## Why we need this

RayBot offers a documented secondary notification source, but account entitlement and evidence quality must be proven before enabling it alongside Helius.

## What to do

- Produce a capability-by-capability GO / PARTIAL / BLOCKED decision for wallet import, Solana webhooks, metadata, positions, and aggregate signals.
- Keep Helius as the qualified chain/recovery path; this optional qualification must not block the first website release.

## How to implement

1. Read the RayBot assessment and current Helius source contract. The owner reports Pro 200; the custom-webhook documentation lists 3 slots for that tier. Verify the actual entitlement, API access, webhook limit/used slots and applicable notification caps using owner-provided configuration. Do not infer the tier from payment amount or confuse Discord webhook limits with custom HTTPS callbacks.
2. Use server-side API credentials from ignored local configuration. Start with read-only list calls. A later live capture must be explicitly opted in: propose at most 3 existing watched Solana wallets, 10 minutes, 100 accepted events and 30 control-plane requests, paced below the documented API limit. Record provider limits separately from client bounds. No upgrade, purchase, overage or unrelated destination changes.
3. Use an isolated temporary HTTPS receiver for the bounded experiment; document and clean up only its own destination. Preserve raw captures privately and sanitize approved fixtures with provenance. Documentation examples are vendor examples, not our live captures; placeholder signatures cannot serve as independently verified transactions.
4. Resolve signature-versus-UUID delivery headers, ID stability across retries/destinations, verification timeout differences, retry schedule/retention and event ordering. Determine slot/commitment, timestamp meaning, execution/instruction identity, actor attribution and parser failures. Do not synthesize missing fields.
5. Compare actual raw token quantities/decimals, SOL versus WSOL representation, fee-inclusive owner deltas versus trade legs, price timestamps and position units against qualified chain responses. Record rounding/conflicts, missing opening history and corrections. Confirm signal schemas and identities separately.
6. Record the destination and global/per-wallet filter configuration, burst grouping, signal-only settings, auto-pause and expiry behavior. Deliberate silence is not complete coverage. Test repeat delivery and a bounded interruption only on the isolated destination; report unrecoverable RayBot gaps honestly.
7. Verify whether a supported history/export path exists and what personal storage/use is allowed. No public history/replay API was found in this docs review. Preserve unanswered questions as capability blockers, not an assumed negative provider answer.
