# [WO-034] Compare RayBot Multi Wallet and Accumulation signals with local research

**Assessment:** [RayBot feasibility review](https://github.com/nhattruong0204/wallet-observer/blob/main/docs/raybot-integration-assessment.md).

## Why we need this

Provider-generated signals can complement our personal consensus engine without being mistaken for additional executions or identical algorithms.

## What to do

- Store and display qualified multi_buy and accumulation observations as an optional research comparison.
- Support a reviewed manual signal CSV import only if a real export format is qualified; never scrape Telegram messages or RayBot private web endpoints.

## How to implement

1. Capture real signal payloads and identities first. Public docs describe aggregate blocks without a complete field contract. Record preset, destination, grouping scope, participants, window, source time, units and rule version when available; unknown fields stay unknown.
2. Distinguish independent wallets from tag/bot groupings and repeated buys. An aggregate contains references to activity, not extra executions. Do not infer person-level consensus from a tag or funding link.
3. Compare with #20 only when participant scope, time basis, thresholds, prices, holding definition and lateness policy are compatible. Show differing or incomparable outcomes without rewriting the local signal algorithm to imitate an undocumented implementation.
4. Keep provider signal IDs and delivery IDs separate; qualify stable deduplication for retries, multiple presets and corrections. Replays/imports must not trigger alert storms. Default to website-only observations; any optional #14 alert path must use expiry/cooldown and explicit settings.
5. Review actual CSV field units, time zone, duplicate keys and aggregation scope. ATH-based potential gain is hindsight, not realized PnL or an executable backtest result. No Bloom auto-buy, signing key, private endpoint, public KOL-universe expansion or runtime AI dependency.
6. Document burst grouping, non-signal suppression and filter settings. Unusual Behavior, token-price/migration alerts and other families remain disabled until their delivery schemas are separately qualified.
