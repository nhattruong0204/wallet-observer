## Why we need this

Stable identities and transactional persistence prevent duplicated trades, mismatched tokens, and lost work when the collector or API restarts.

## What to do

- Create the initial relational schema and migrations for watches, identities, source records, events, executions, quotes, checkpoints, jobs, and notifications.
- Define uniqueness constraints, precision, event revisions, and a committed delivery sequence.

## How to implement

1. Use chain plus canonical address for wallets/tokens; preserve Solana case. Separate human labels from evidence-bearing account-wallet links.
2. Deduplicate raw source IDs and economic executions with chain/signature/instruction identity where available. Store raw payloads with bounded retention.
3. Use integer/high-precision numeric quantities and decimal values; store UTC timestamps and explicit unknown/missing states.
4. Write canonical mutations and an outbox row in the same transaction. A single ordered dispatcher must assign/persist a committed delivery sequence; do not use a pre-commit sequence as the replay watermark.
5. Implement migrations and indexed access paths. Keep jobs claimable with a lease and bounded retries; one process may still crash mid-job.

## Definition of done

- [ ] Migrations apply to an empty database and an upgrade path is documented.
- [ ] Duplicate fixture ingestion does not create extra executions.
- [ ] Two distinct same-amount swaps remain distinct.
- [ ] A rollback does not advance the safe source checkpoint or emit a phantom committed event.
- [ ] Precision, address case, and chain separation survive a database round-trip.
- [ ] No user, billing, entitlement, quota, or session tables are introduced.
