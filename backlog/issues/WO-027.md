## Why we need this

Multi-chain support should reuse the product model while acknowledging that receipts, routes, confirmation, and provider coverage differ by network.

## What to do

- Select the next genuinely needed network and document a per-chain capability/cost decision.
- Implement and validate adapters one chain at a time rather than enabling every chain label seen in Wind.

## How to implement

1. For each candidate, verify network ID, environment, official RPC/indexer source, transaction decoding, history, quote coverage, and usage cost. Create a chain-specific checklist before coding.
2. Implement the shared adapter contract using receipts/logs or qualified decoded transactions; define token identity, address normalization, finality, and reorg behavior.
3. Reuse recovery, canonical revisions, filters, notification rules, and exact chain/address search.
4. Treat bridge transfers and cross-chain order legs explicitly; do not turn every bridge receipt into a purchase.
5. Keep unsupported networks behind disabled capabilities. Record actual coverage instead of claiming generic EVM support automatically works everywhere.

## Definition of done

- [ ] Each enabled network has a published capability matrix and representative real/sanitized fixtures.
- [ ] Same-address tokens on different chains remain distinct.
- [ ] Reorg/failure/correction and restart recovery scenarios behave correctly.
- [ ] Trade attribution and market values are verified against the chosen chain source.
- [ ] Cost and latency are measured before increasing the watch universe.
- [ ] Networks without a qualified source remain out of the enabled configuration.
