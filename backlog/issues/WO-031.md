# [WO-031] Persist authenticated RayBot webhooks with source health controls

**Milestone:** Optional RayBot

**Status:** Planned; enable only after the required RayBot capability passes qualification. Optional to first-live delivery.

**Website first:** Desktop-browser website and supporting services only. Native mobile, installable PWA, device push and mobile acceptance remain deferred. Monitoring is read-only; no execution, signing keys, new chains or subscription upgrades are authorized.

**Assessment:** [RayBot feasibility review](https://github.com/nhattruong0204/wallet-observer/blob/main/docs/raybot-integration-assessment.md).

## Why we need this

RayBot callbacks must survive restarts and retries without exposing the private dashboard or trusting unverified event facts.

## What to do

- Add one optional authenticated HTTPS ingestion route on the existing API and durable processing in the existing worker/PostgreSQL.
- Expose RayBot destination health and an operator runbook; deployment activation uses #17’s private-access boundary.

## How to implement

1. Keep RayBot disabled by default. Require an independent high-entropy callback secret, HTTPS and constant-time authorization validation. User-Agent is diagnostic only. Do not invent HMAC signatures, trusted IP ranges or provider certificates absent a verified contract.
2. Accept the verified test event separately without creating a trade. For accepted activity, atomically persist the source envelope, payload representation and job before returning 2xx. Bound body size, parse depth and work; target an acknowledgement below one second and process heavy work asynchronously.
3. Keep delivery attempt ID, destination, chain transaction ID and payload hash distinct. A signature may carry multiple wallet/event representations, while a retry may have a different transport ID. Preserve distinct evidence and make duplicate processing harmless according to the qualified contract.
4. Return retryable failure for temporary persistence failures. Persist bounded quarantine for authenticated unknown schemas where possible, then alert on incompatibility. Define permanent rejection deliberately because documented 4xx responses are not retried; include overload and disk-full behavior.
5. Reuse existing source-health/retention mechanisms from #16. Record receipts, duplicate counts, queue age, rejected/quarantined events, destination send/pause/expired status and failure count. Silence alone cannot prove a fault or completeness; reconcile health with a paced control-plane status read.
6. Provide reviewed provisioning/rotation/pause/removal instructions for a dedicated destination. Pause/resume affects attached wallet state; do not automatically resume after repeated failure. Register only the selected watch subset, respect shared API budgets, and isolate the public callback route from all private app/admin endpoints.

## Definition of done

- [ ] Valid authorized callbacks persist and enqueue atomically; unauthorized and oversized requests fail without leaking payloads or credentials.
- [ ] Duplicate, out-of-order and unknown inputs plus worker/API crashes have deterministic PostgreSQL tests.
- [ ] A live bounded acceptance records acknowledgement latency, retry behavior and recovery after restart; no fabricated provider SLA.
- [ ] Private routes remain inaccessible from the public callback surface and disabling RayBot leaves Helius operating.
- [ ] Auto-pause/expiry, rotation, retention and unresolved gaps are observable and documented; no automatic trading or external sends.
