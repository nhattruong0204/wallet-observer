## Why we need this

Preview, pending, refund, failure, and revocation describe source order state; they are not interchangeable with blockchain confirmation.

## What to do

- Implement a source-evidenced order lifecycle only for capabilities proved in WO-023.
- Link orders and execution legs conservatively, preserving uncertain matches and corrections.

## How to implement

1. Keep off-chain order status and chain confirmation in separate fields and state machines.
2. Match by stable source order ID or transaction references. Use explicit confidence/evidence for weaker associations; never merge solely on similar time/amount.
3. Handle partial fills, refunds, revocations, and source corrections with reversible contributions to positions and signals.
4. Display attempted orders distinctly and make failed attempts ineligible for confirmed volume/consensus.
5. For multi-chain orders, retain separate legs until the selected chain adapters can establish the final economic outcome.

## Definition of done

- [ ] Fixtures cover successful, failed, refunded, revoked, unmatched, and duplicate order updates where the source supports them.
- [ ] A failed attempt that never reached the chain is shown only from an actual upstream record.
- [ ] Execution finality does not automatically imply the intended off-chain order succeeded.
- [ ] Corrections update existing cards and derived totals rather than adding duplicate economic events.
- [ ] Unavailable lifecycle states stay disabled or unknown.
