# [WO-014] Deliver alerts to one Telegram chat with durable retries

<!-- wallet-observer-task:WO-014 -->

**Milestone:** First live

**Plan:** [BUILD_PLAN.md](https://github.com/nhattruong0204/wallet-observer/blob/main/BUILD_PLAN.md)

## Why we need this

One outbound channel lets you use the tracker without keeping its dashboard open. Reliability requires more than a direct send inside the collector.

## What to do

- Implement one server-configured bot token and destination chat.
- Queue eligible new trades for delivery with filtering, retries, deduplication, and stale-event expiry.

## How to implement

1. Write notification intent transactionally and process sends in the worker. Keep bot tokens in server-side secrets and use a manual test-message action.
2. Define direction, wallet/group, amount, and optional token filters with a versioned rule snapshot. Recheck mutable rules before delayed sends.
3. Use canonical event ID plus destination as the notification identity; store Telegram message IDs for supported corrections.
4. Respect retry-after responses and backoff. Distinguish definite failures from uncertain acknowledgment timeouts; document the chosen resend tradeoff.
5. Suppress historical replay and stale alerts; keep operational delivery errors separate from successful trade events.

## Definition of done

- [ ] A qualifying real event reaches the configured chat with token, wallet, amount, time, and explorer link.
- [ ] Duplicate ingestion does not normally create a second notification.
- [ ] Rate-limit/transient failures retry without blocking ingestion.
- [ ] Backfill and database restore do not resend the entire history.
- [ ] The UI never receives the bot token, and no Bark/audio/multi-customer binding system is introduced.
- [ ] The runbook explicitly avoids an exactly-once delivery guarantee.
